Journey: play a song

What the user does and sees

The user opens an album page and clicks a song row. Music.app starts to play that song, with the rest of the album after it in the queue. The player bar at the bottom of the window then shows the song's name, cover and position.

One click plays the row. The Signal of a box holds a click count, but the album row does not read it. The "Play" button above the songs takes the same path from the first song.

This page follows the click through the code. It uses ideas that the index page explains:

  • Odin and its memory.
  • The frame loop and the immediate-mode UI.
  • Metal and Objective-C calls from Odin.
  • The helper process and the SQLite file.

The journey, step by step

Use Next and Back, or the arrow keys, to follow the click. Click a box to read what it does.

Each step in the code

1. The mouse press reaches the app

run waits for the next AppKit event. It gives each event to take_event first. For a left mouse down, take_event stores a Mouse_Press with the position, the button, the click count and the modifier keys. It then calls request_frame, which starts the display link (request_frame). See Objective-C calls and the window page.

This step runs on the main thread, between two frames.

2. The release, and a new frame

For a left mouse up, take_event stores a Mouse_Release. On the next refresh of the screen, run_frame calls on_frame. The app set on_frame to draw_frame. After the frame, run_frame empties the list of events.

The press and the release can come in one frame or in two. Each frame reads the events since the last frame.

3. The UI finds the clicked box

draw_frame calls ui.begin_frame. begin_frame sets clicked_key to 0, then calls apply_events.

In apply_events, the press makes the box under the mouse the active box. The release over that same box makes it the clicked box. The box under the mouse comes from find_hot. end_frame calls it, so it uses the boxes of the last frame. See the immediate-mode UI.

This step runs at the start of the frame after the release.

4. The album page builds the row

The album page calls build_numbered_songs with the album's songs. build_numbered_songs builds one row box per song, with the .Clickable flag. The ID of each row holds the index and the song's ID, so the row keeps its key from frame to frame. ui.signal compares the row's key with the clicked key and sets is_clicked. See the pages page.

This step runs on the same frame, while the app builds the page.

5. The row asks the queue to play

The row gives its signal to apply_song_row_signal. That procedure opens the song menu on a right click. It starts a drag when the user holds the button and moves the mouse. It returns true for a click, unless a drag ended on this frame. The row then calls playback.play_songs with the album's songs and the row's index.

This step runs on the same frame.

6. play_songs fills the queue

play_songs returns at once for an empty list. With shuffle off, it puts copies of the songs in the queue and calls play_at with the clicked index. With shuffle on, list_play_order puts the clicked song first, and play_at starts from 0.

The queue keeps its own copies. The page reads its songs into new memory when its answers or phase change, so the queue never points into the page's memory. The old songs wait until the next frame starts, when free_retired_songs frees them. See memory.

This step runs on the same frame.

7. play_at asks the helper to play

play_at counts one more play in play_count. set_playable puts the Apple match in place of a YouTube song that has one. play_at sets the queue index and empties playing_persistent_id. save_queue_and_handoff writes the queue to the SQLite file through save_queue.

to_song_match turns the song into a Song_Match: the name, the artist, the album, the length and a YouTube ID. send_play wraps it in a playSong command with a new request ID. play_at keeps the request ID with the kind .Play and the play count.

This step runs on the same frame.

8. The command goes to the helper

send returns at once if the helper did not start. Else it locks write_mutex, as worker threads send too. It writes the command and a newline to the helper's stdin. See the helper process.

In the helper, startReadingCommands runs a thread that reads each line. It decodes the line as a Command and gives it to the main queue.

The app writes the line on the same frame. The helper reads it on another thread, in another process.

9. The helper tells Music.app to play

The helper's playSong case checks for a YouTube video ID. An album song has none, so the helper stops its YouTube page and calls music.playSong.

MusicApp.playSong calls findSong. findSong runs an AppleScript that lists the library songs with the same name, artist and album. It picks the one closest in length and returns its persistent ID. play(persistentID:) then runs a second AppleScript that plays the song with that ID.

This step runs on the helper's main thread, in another process.

10. The helper answers playSongResult

After the play script, the helper sends playSongResult. It holds the request ID and the persistent ID, or null when findSong found no song. send writes each message as one JSON line to the helper's stdout.

This step runs on the helper's main thread, in another process.

11. Music.app posts playerInfo

Music.app starts the song. It then posts the com.apple.Music.playerInfo notification. The helper observes that notification. It then sends the result of readNowPlaying.

readNowPlaying runs an AppleScript for the state, the volume, the position, the name, the artist, the album, the persistent ID and the length. It saves the cover to a file and puts its path in artworkPath. The result goes to the app as a nowPlaying message.

Music.app posts in its own process. The helper reads and sends on its main thread.

12. The app reads the helper's lines

start runs read_lines on a thread of its own. read_lines reads the helper's stdout and stores each full line. It then calls platform.wake.

wake posts an application event to AppKit. take_event sees .ApplicationDefined and asks for a frame.

read_lines runs on another thread of the app. The frame it asks for is a later frame.

13. apply_helper_messages takes in the answers

At the start of each frame, apply_input calls apply_helper_messages. It calls take_messages, which reads each stored line as JSON. helper.apply runs for each message.

  • For nowPlaying, apply sets the playback state and the position. It puts a copy of the song in core.app.now_playing.
  • For playSongResult, the frame calls apply_queue_answer. For the kind .Play, it drops an old answer. It keeps the ID as queue.playing_persistent_id.
  • For nowPlaying, the frame also calls apply_queue_now_playing. For a playing song, apply_playing_song keeps the song and its position in queue_state.tracking.

This step runs at the start of a later frame, before the app builds any box. See the playback page.

14. The player bar shows the song

Later in the same frame, draw_frame calls build_player_bar. build_song_info gets the song from find_shown_song. That procedure returns now_playing's song while Music.app plays or pauses.

The cover comes from Apple's artwork of the queue song, when the queue plays it. build_progress gets the position from to_position_seconds. That procedure moves the position on with the clock between the helper's messages. The helper also sends the position every 2 s. See the player page and Metal, which draws the boxes.

This step runs on the same later frame as step 13.

15. The row shows the playing song

The album page asks find_queue_song for the song of now_playing. find_queue_song finds it when its persistent ID equals queue.playing_persistent_id. The clicked row then gets the accent tint and an accent number.

This step runs on the same later frame, while the app builds the page.

When the path changes

Music.app is not open

MusicApp.playSong checks isRunning first. When Music.app does not run, launch opens it with activates = false, so it stays behind onlymuse. findSong and the play script then run as in step 9. When Music.app starts, the helper also sends the result of readNowPlaying.

If findSong finds no song in the library, playSongResult holds no ID. apply_queue_answer then sets is_adding and calls start_adding. On a thread, start_adding asks Apple to put the song in the library. update_queue then sends playSong every 1.5 s, for up to 45 s. Meanwhile the player bar shows "Adding to library…".

The song is a YouTube song

A song row on a YouTube page calls the same play_songs. In play_at, set_playable asks find_playable for the Apple match. With a match, the Apple song takes its place and plays from Music.app as above. That song must start within 8 s, or fall_back_to_youtube plays the YouTube song.

With no match, to_song_match puts the video ID in the command. The helper then calls youTube.play. It pauses Music.app and loads the song in its hidden music.youtube.com page. It sends a nowPlaying with isLoading, and answers "yt:" and the video ID as the persistent ID. The player bar shows "Loading from YouTube…" until the page plays the song.

Pages and their data

This page follows one page of the window from a click to the songs on the screen. It covers the data under each page. It does not cover how a frame draws. For that, read The window and a frame. For what happens after a click on a song, read Playback.

What you see

The sidebar on the left lists the pages in four groups:

  • Apple Music holds Home and New.
  • YouTube Music holds Mixes, Liked Music and Bring Over.
  • Library holds Favourite Songs, Recently Added, Artists, Albums, Songs and Downloaded.
  • Playlists holds the library playlists of the account.

Home and New show shelves. A shelf is one named row, such as Made for You. Each tile on a shelf is a card: an album, an artist, a playlist or a song. Home shows Apple's shelves and YouTube Music's shelves in turn. A YouTube shelf has YouTube's mark before its name.

A click on an album card opens the album page. The page shows the cover, the title, the artist and badges such as "LOSSLESS" and "In Library". Under them are the Play and Shuffle buttons and a numbered row for each song. A playlist page and the library song pages show a list of song rows. Each row has a small cover, the name, the artist and album, a heart and the length.

A right-click on a song row opens the song menu. It holds "Play Next", "Add to Playlist", "Favourite", "Go to Artist" and "Copy Link", and some more items for YouTube songs. Cmd K opens the command palette. Its field says "Go to a page, an artist, a song, or do something". The palette finds pages, playlists, library artists, albums and songs, and Apple Music's catalog.

While a page waits for its data, it shows "Loading…". When Apple refuses and the app has no saved answer, the page shows "Apple Music could not be reached."

From a click to the songs on the screen

The window builds every box again in each frame. If that idea is new to you, read immediate-mode UI and the frame loop first. So a page never "loads" once. In each frame, the page asks for its data again and shows what there is so far. Step through the diagram, or click a box.

Apple, YouTube and the cache they share

The app reads two outside services. src/apple is the one package that asks amp-api.music.apple.com. src/youtube is the one package that asks music.youtube.com. Both go through one cache and one SQLite table.

Navigation

A Page holds a kind, an ID and a title. The ID is a playlist, album or artist ID, or the search term. Page_Kind lists every page the window can show.

The history is a list of pages, with one scroll position for each, and an index. navigate drops the pages that Forward would show, then appends the new page. It keeps at most MAX_PAGE_COUNT pages, which is 50. navigate clones the ID and the title. A card's text lives in its page's arena, and the app can free that arena later.

Every change to the history calls save_navigation. It writes the history as JSON under the state key "navigation". At the next start, start_navigation reads it back, with Back and Forward as they were. With no saved history, the window opens on Home.

The sidebar calls navigate when the person clicks a row (sidebar.odin). The search field calls it with a Search page (search_field.odin). A card calls it through open_card.

In each frame, build_page_area builds the Back and Forward buttons and then the current page. build_page holds one switch case for each kind. The page's scroll box gets its saved place back through keep_scroll. The content may still load, so keep_scroll sets the place again for up to 2 s.

Page data and arenas

A page calls apple.watch in every frame. Reading a large JSON answer in every frame costs too much time. So a page reads each answer once and keeps the result in a Page_Data. Page_Data has fields for what pages show: a title, shelves, cards, songs, badges and more.

Each Page_Data owns an arena. If arenas are new to you, read memory in onlymuse. find_page_data takes a key, a signature and a phase:

  • The key is the path the page watches.
  • The signature is a number made from the versions of the answers. A page that watches two answers mixes both versions into one number.
  • When the signature or the phase differs from the stored one, find_page_data returns a fresh, empty Page_Data with is_stale true.

The page then reads the answer into that arena. For an album, read_album reads the title, the artist, the songs, the detail line and the badges. It uses page_allocator for each string.

Boxes point at the page data's text until the frame ends. So find_page_data never frees the old arena at once. It hands the arena to retire_arena. At the start of the next frame, free_retired_memory frees it. The same procedure frees the page data of a page that no frame asked for in UNUSED_PAGE_MS, five minutes. The answers stay in the store, so that page comes back at once.

The library lists use page data too. list_library_songs, list_library_albums, list_library_artists and list_playlists each return what the library holds so far. Apple sends a library list 100 items at a time. watch_all_pages watches one path for each part and follows Apple's offset to the next part.

The cache and the SQLite store

apple.watch returns a Watched: a phase, a body, a version and a status. The Phase is Loading, Ready or Failed. The version counts up each time a newer body replaces the old one.

For a path it has not seen, watch does three things:

  1. It looks in the store with find_answer. A saved answer makes the entry Ready at once.
  2. It compares the saved answer's age with fresh_rules. A catalog answer stays fresh for 24 hours. Recommendations stay fresh for 10 minutes. Any other /v1/me/ answer is never fresh.
  3. When the answer is missing or old, it gives the path to check on a pool of CHECK_THREAD_COUNT threads, which is 4.

check runs on a worker. It gets the answer and, on status 200, saves it with save_answer. A new body gets a new version. A failed check keeps the saved answer, so the app works offline. Then check calls platform.wake, so the window builds a frame that shows the change. A failed path gets a new try when a page watches it 30 s after the failure (FAILED_RETRY_MS).

A write to the library calls refresh. It asks again for one path and keeps the saved body until the new one comes. A YouTube sign-in calls refresh_all with the prefix youtube/. The cache frees a replaced body one frame later, in free_retired_bodies. It lets go of an answer no page watched in five minutes.

Apple's requests go through send_request. It sends the developer token and the user token, which the helper reads from a hidden music.apple.com page (set_tokens). For the helper, read the helper. On 401 or 403, send_request asks the helper for fresh tokens and sends the request one more time. In the first 30 s after the start, a request waits for the tokens (TOKEN_WAIT).

net.fetch sends each HTTP request through libcurl. Each thread keeps its own curl handle, so curl reuses its connections. It waits at most 15 s (TIMEOUT_MS). On no answer, 429 or a 5xx status, it tries a GET again after 250, 500 and 1000 ms. It never tries a POST again, as a second POST could put a song in the library twice.

The store is one SQLite file in ~/Library/Application Support/onlymuse-native. If SQLite is new to you, read SQLite. SCHEMA makes five tables:

  • responses holds each answer by its path.
  • plays holds the play log.
  • state holds saved values as JSON, such as the history and the panel (save_state).
  • matches and rejected_matches hold the Apple Music song each YouTube song is.

The worker threads and the main thread share one connection. start opens it with SQLITE_OPEN_FULLMUTEX, which lets several threads use it.

YouTube lists

src/youtube speaks YouTube Music's web API. A YouTube path looks like youtube/browse?{"browseId":"FEmusic_home"}. The JSON after the ? is the request body. youtube.start registers send_request for the prefix youtube/ with apple.add_source. So YouTube's answers go through apple's cache and the same SQLite table.

With a sign-in, send_request sends the cookie that the helper read from the Helium browser. It signs each request with to_authorization, a SHA-1 of the time, the SAPISID cookie and the origin. apply_youtube_cookie takes in a new cookie. When the sign-in changes, it asks again for every YouTube answer.

to_list reads any browse, search or next answer into a List: a header, songs, shelves, cards and a continuation token. The songs and cards use apple's own Catalog_Song and Card types. So one song row or one card works for both services. A YouTube song has the ID yt: and its video ID.

src/app/youtube_lists reads YouTube's answers for the pages:

  • watch_youtube_list watches one path and reads its List once for each version, into an arena of its own.
  • watch_youtube_songs follows the continuation tokens of a long list, up to 50 parts. It copies every song into one Page_Data with copy_song.
  • watch_youtube_home reads up to 6 parts of YouTube's home. merge_youtube_shelves puts its shelves between Apple's on Home.
  • watch_youtube_artist finds the YouTube channel with an artist's name, for the artist page.
  • merge_playlist_youtube_songs puts the YouTube songs that onlymuse keeps for a library playlist among its Apple songs. Apple's playlists hold only Apple songs.

The YouTube pages use these. build_youtube_playlist_page shows Liked Music and any YouTube album, playlist or mix. build_youtube_mixes_page picks the mixes from YouTube's home. A mix is a playlist with an ID that starts with "RD" or "VLRD". On the search page, build_youtube_search_results shows "From YouTube" songs that Apple lacks, and "Videos on YouTube".

Cards and rows

src/app/lists holds the cards, song rows and grids that more than one page shows. They take the data a page already read and build boxes. They never watch a path themselves.

  • build_shelf builds one shelf from Apple or YouTube. A shelf of videos gets wide tiles in 16:9.
  • build_card_row builds only the tiles in view, plus 2 on each side. Empty boxes keep the width of the other tiles.
  • build_card_tile builds the cover, the name and the subtitle of one card. It returns true on a click.
  • open_card opens the card's page. A song card plays the shelf's songs from that song.
  • build_song_list_page builds Favourite Songs, Songs, Downloaded, every playlist and an artist's Recent Songs.
  • build_song_rows builds only the rows on screen. Tall empty boxes stand in for the rows above and below.
  • build_song_row builds one row. The song that plays now gets the accent colour.
  • build_row_heart shows the heart. A YouTube song with no match shows YouTube's mark.
  • build_card_grid builds rows of whole tiles, such as the Albums and Recently Added pages. It builds only the rows on screen.

The song menu

Every song row reports its signal to apply_song_row_signal. A right-click there calls open_song_menu, which keeps a copy of the song. A press that moves more than 6 points starts a drag instead. A sidebar playlist under the dragged song takes it on release (apply_song_drop).

The frame builds the menu after the page, over everything else, in build_song_menu. A click outside the menu or Escape closes it. "Add to Playlist" opens a second menu of playlists, from build_playlist_menu.

add_to_playlist sends an Apple song to Apple. A song only on YouTube goes into onlymuse's own part of the playlist instead. The write to Apple blocks, so start_write starts a thread for run_write. That thread calls apple.post and stores the toast text and the path to ask again. Once a frame, apply_write_results shows the toasts and calls apple.refresh on those paths. The playlist page then shows the new song.

The command palette

Cmd K calls toggle_palette. While the palette is open, build_palette runs in each frame, after the page and the song menu.

update_results builds the results from data the app already has:

  • "Actions", such as "Play or Pause" and "Show Lyrics".
  • "Pages", from the sidebar's items, and "Playlists", from list_playlists.
  • "Artists", "Albums" and "Songs", from the library lists of core.
  • "Apple Music", from a catalog search with at most 4 results of each type.

The catalog search waits until typing stops for 300 ms (PALETTE_SETTLE_MS). update_results makes one signature from the term and the versions of all that data. When nothing changed, it keeps the last results. Otherwise it builds them again in a fresh arena and retires the old one, as find_page_data does. list_best_indexes puts a name that starts with the term first. run_result navigates, plays a song, opens a card or runs an action, as the chosen result asks.

Where the code is

  • src/app/core/navigation.odin holds the history, Back, Forward and the saved scroll.
  • src/app/core/page_data.odin holds Page_Data, its arenas and the frees at the start of a frame.
  • src/app/core/library.odin holds the library's songs, albums, artists and playlists.
  • src/app/core/songs.odin copies songs, cards and shelves from one arena to another.
  • src/app/core/sidebar_items.odin lists the pages of the sidebar.
  • src/app/pages.odin picks the procedure that builds the current page.
  • src/app/browse/ holds the Apple Music pages: Home, New, albums, playlists, artists, the library, downloads and search.
  • src/app/youtube_pages/ holds the YouTube pages, the YouTube sign-in and Bring Over.
  • src/app/youtube_lists/ reads YouTube's lists for the pages and keeps YouTube songs in Apple playlists.
  • src/app/lists/ holds the shelves, cards, song rows and grids.
  • src/app/menus/ holds the song menu, the playlist writes and the drag of a song.
  • src/app/palette/ holds the command palette and its results.
  • src/apple/apple.odin holds the tokens and the requests to Apple's API.
  • src/apple/cache.odin holds watch, the worker threads and the fresh rules.
  • src/apple/resources.odin reads Apple's answers into songs, cards and shelves.
  • src/youtube/youtube.odin holds the paths and the requests to music.youtube.com.
  • src/youtube/resources.odin reads YouTube's answers into a List.
  • src/store/store.odin holds the SQLite file: answers, the play log, saved state and matches.
  • src/net/net.odin sends HTTP requests through libcurl.

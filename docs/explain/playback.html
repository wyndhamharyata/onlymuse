Playback

This page explains how onlymuse plays songs. onlymuse draws no sound itself. Music.app plays each Apple Music song. A hidden music.youtube.com page plays a YouTube song that Apple Music does not have.

The page uses some ideas that the index page explains. Read these first if they are new to you: Odin, memory in Odin, the frame loop, immediate-mode UI, Objective-C calls, the helper process and the SQLite file. The journey page follows one click on Play through every part of the app.

What you see and hear

  • You click a song in a list, or Play on an album. Music.app plays the song. When Music.app is not open, onlymuse opens it in the background.
  • Music.app keeps no queue after a song that AppleScript starts. So onlymuse keeps its own queue. The Up Next tab of the side panel shows it.
  • When a song ends, the next song of the queue starts at once. Music.app's own Autoplay never plays.
  • The shuffle button orders the queue by rules. A right click on it opens the "Shuffle" menu of those rules.
  • A YouTube song plays from Apple Music when it has a match. Without a match, a hidden music.youtube.com page plays it. Music.app pauses meanwhile.
  • When Music.app stops or quits, the player bar shows the last song, paused where it stopped. Play starts it again from that point.

The helper and its messages

The app starts the helper in start. The two processes speak JSON lines over the helper's stdin and stdout. One message is one line. Message names every field the helper sends. Command names every field the app sends.

A thread in the app, read_lines, reads the helper's lines and wakes the window. Each frame, take_messages hands the main thread the lines so far. send writes a line the other way. It holds a mutex, as worker threads send too.

These are the messages of playback that the app sends:

MessageWhat it asks
playSongPlay this song now. send_play sends it. The answer is playSongResult.
setNextStart this song when the one with this persistent ID ends. send_set_next sends it. The answer is setNextResult.
playPause, seek, setVolume, next, previousControl the player. The helper sends the first three to the YouTube page while a YouTube song plays.
trackInfoWhat Music.app knows of a song. send_song_info_request sends it.
setFavoriteSet or clear a song's favourite in Music.app. send_set_favorite sends it.
refreshTokens, signIn, youtubeSignInRead the Apple tokens again, show the Apple sign-in, or read Helium's YouTube cookies again.

These are the messages the helper sends:

MessageWhat it holds
nowPlayingThe state, the song, the position and the volume. The helper sends it after each playerInfo post, after a seek or a volume change, and when the YouTube page changes state.
positionThe position alone, every 2 seconds while a song plays. Music.app posts nothing as a song plays.
playSongResult, setNextResultThe request ID and the song's persistent ID, or null.
trackInfo, setFavoriteResultThe answers to trackInfo and setFavorite.
youtubeCookieHelium's youtube.com cookies, or an empty text and a problem.
accent, tokens, signInNeeded, errorThe system accent colour, Apple's tokens, a request to sign in, and a text for the Console page.

apply_helper_messages sends each message to the code that owns it. apply keeps the now playing state. Between two posts, to_position_seconds counts the position on from the time the helper read it.

Inside the Swift helper

The helper is a small AppKit app with no Dock icon. main.swift reads each command and calls one of these parts:

  • MusicApp runs AppleScript with NSAppleScript. Each script checks first that Music.app runs, so a read never opens Music.app. findSong looks up a library song by its name, artist and album.
  • The helper listens for Music.app's com.apple.Music.playerInfo post. Music.app sends it on a pause, a play or another song. One timer checks the volume every 2 seconds. Another timer sends the position every 2 seconds while Music.app plays.
  • YouTube keeps music.youtube.com in a page that no one sees. WebKit plays a page's media only inside a window. So the page has a clear window far off every display.
  • readYouTubeCookies reads the youtube.com cookies of the Helium browser. Google refuses a sign-in inside an app's own page. The helper reads Helium's key from the Keychain. macOS asks the person once.
  • sendCookie sends those cookies to the app as youtubeCookie. It also puts them in WebKit's cookie store, so the YouTube page plays signed in.
  • WebPlayer keeps a hidden music.apple.com page. It reads the developer token and the user token from it. Its window shows only to sign in.
  • LocalProxy listens on 127.0.0.1. Both pages connect through it, so neither uses HTTP/3. Some networks allow IPv6 packets only up to 1280 bytes. HTTP/3 sends larger ones.

When the app quits, the pipe closes. The helper then pauses Music.app and the YouTube page in pauseWhenAppEnds. A test run sets GPUIX_BACKGROUND=1. The helper then keeps the music as it is.

The queue and the handoff

The queue is Queue_State. It holds copies of the songs, the index of the song playing, shuffle, repeat, and the persistent ID that Music.app gave the queue's song. The store saves it under the key queue, and start_queue reads it back at start.

A page calls play_songs or shuffle_songs. "Play Next" in the song menu calls play_next. Each one ends in play_at, except play_next when a queue already plays.

The handoff starts the next song without a pause:

  1. sync_handoff sends setNext whenever the song playing or the next song changes. With repeat one, the next song is the same song.
  2. Handoff.set finds the next song's persistent ID in the library.
  3. arm sets a timer for 0.4 seconds before the end. It reads the position again then, as a seek or a pause moves the end.
  4. fire starts the next song 0.04 seconds before the end. Music.app's own switch takes longer, so Autoplay never plays.
  5. When Music.app switches to a song of its own within 3 seconds of the end, onPlayerChange starts the next song at once.
  6. In the app, apply_playing_song sees the handoff song start. It moves the queue's index. It sends no playSong.

When a song ends with no handoff, play_next_after_end plays the next song. A song counts as ended within 3 seconds of its end.

A catalog song that is not in the library gets the answer null. start_adding then asks Apple's API to put it in the library. update_queue sends playSong again every 1.5 seconds, for at most 45 seconds.

update_queue also watches for a song that does not move on. After 2 still positions, about 4 seconds, restart_stalled_song plays it again. A song still at 0:00 gets 8 positions, about 16 seconds. The queue tries this at most twice.

The queue leads only while Music.app plays the queue's song, or while the queue puts a song in the library. Otherwise skip_to_next sends next. Music.app's own order then applies. is_queue_leading decides it.

The resume point

The Resume_Point holds the last song Music.app played and its position. apply_resume_point saves it on each post, and every 5 seconds while a song plays. The store keeps it under its own key, resumePoint, apart from the queue's songs. A force quit loses at most 5 seconds.

When Music.app stops or quits, find_shown_song gives the player the resume point's song. A click on Play then calls resume_last_song. It sends playSong, then a seek to the saved position. A song that played to its end saves the position 0.

Shuffle and the play log

shuffle_by_rules draws a random order, then applies the rules in shuffle_rules:

  • Songs played in the past 6 hours go last. The menu offers Off, 2, 6 and 24 hours.
  • Songs skipped 3 times or more, and more often than played, go last.
  • Two songs of one album do not play one after the other, where another song can go between.
  • Favourites come earlier, 2.5 times as likely. This rule starts off.

The Up Next tab shows what the rules changed, such as "4 recent songs and 1 often-skipped song play last." toggle_shuffle keeps the song playing first. Shuffle off goes back to the order the songs came in.

The rules read the play log. onlymuse counts plays and skips itself. update_play_log keeps how far each song got. When the song changes, finish_listening decides:

  • A song heard to its middle, or for 4 minutes of a long song, is a play.
  • A song stopped sooner, after at least 2 seconds, is a skip.
  • A song stopped within 2 seconds counts as nothing.

The store saves each play and skip in the SQLite file. The app keeps the last 120 days in play_log, for shuffle and the Now Playing page.

Favourites and song info

toggle_favourite runs on a click on the heart button in a row, the player bar or Now Playing:

  • For an Apple song, it sends setFavorite. setFavorite sets Music.app's favourite, which also puts the song in Favourite Songs.
  • For a YouTube song, it likes or unlikes the song on YouTube.
  • When Music.app has no such song, apply_favourite_answer turns the heart back. It shows "Music.app has no such song in your library. Add it to the library first."

is_favourite reads Music.app's answer for the song first. Then it reads this session's toggles. Last, it reads the Favourite Songs playlist from Apple's API.

watch_song_info asks Music.app what it knows of a song that Apple's API does not. That is the play count, the skip count, the dates, the favourite and the file. It asks at most once a minute for each song. readTrackInfo reads them in the helper.

Matching: a YouTube song finds its Apple song

A YouTube song has the ID yt: and its video ID. A match is the Apple Music song it is. With a match, the song plays from Music.app, lossless. Without one, it plays in the YouTube page.

The parts of matching, in order:

  • find_match answers at once from memory when it can. It starts a request only for a video with no answer yet.
  • is_same_recording holds the rule. One recording has the same cleaned title, the same artist and a length within 3 seconds.
  • to_match_key cleans a title. It keeps lowercase letters and digits only. It drops "feat." and the parts in brackets, such as "(Official Video)".
  • list_title_keys also tries each half of a title around " - " or " / ". YouTube often writes a Japanese title and its romaji that way.
  • find_closest picks the closest in length of the songs that agree.
  • When Apple refuses with 429, finish_job pauses matching for 60 seconds. Each refusal in a row doubles the pause, up to 30 minutes. A song with no answer gets no saved match. find_match checks it again later.
  • MATCH_RULE_VERSION changes with the rule. When it differs from the saved value, the store deletes every saved match.

The person can correct a match. "Not on Apple Music" in the song menu calls reject_match. The song then plays from YouTube from then on. "Try Apple Music Again" calls allow_match.

How a YouTube song plays and falls back

Three things send a song to YouTube:

  1. The song has no match, or its check did not finish before it plays.
  2. The person chose "Not on Apple Music".
  3. Music.app did not start the match. await_start gives it 8 seconds. Then fall_back_to_youtube rejects the match and plays the YouTube song. A toast says Apple Music could not play %s, so it plays from YouTube, with the song's name.

The same fallback runs when the library never gets a song within 45 seconds and the song came from YouTube.

In the helper, YouTube.play does these steps:

  1. It pauses Music.app.
  2. It loads music.youtube.com/watch with the video ID, or tells a page that already loaded to play the song.
  3. It sends a nowPlaying with isLoading, so the player shows the song at once.
  4. poll reads the page every 0.5 seconds. It sends nowPlaying on a change of state, and position every 2 seconds.

The page can fail to start or stop partway. The helper tries again:

  • checkSlowStart asks again after 4 seconds with no start. The second time, it opens the page again with new network connections. After that, the player shows the song paused.
  • checkStuck loads the song again where it stopped, after 10 seconds stuck. After 2 tries, the player shows it paused.

A YouTube song after a Music.app song loads ahead, muted and paused. prepare does that, so the song starts at once when its turn comes. The page closes 5 minutes after the last YouTube song, as it holds 200 MB or more. It stays open while the queue has a YouTube song ahead, as keepsYouTube in setNext says.

Music.app takes the player back only when it plays a song again. The playerInfo observer then calls YouTube.stop, which pauses the page.
